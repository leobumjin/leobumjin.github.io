## 1. Why Verified AI?

How should we trust something generated by an AI? Most approaches to AI reliability try to improve the model itself through better training, longer reasoning, self-correction, evaluation, or interpretability. Yet even if a model becomes much stronger, one question remains: **how do we know that the generated result is actually correct?**

Max Tegmark discusses a related direction through **vericoding**. Rather than stopping at code generation, vericoding asks an LLM to generate programs whose correctness can be checked against a **formal specification**. <citation key="bursuc2025vericoding"></citation>

The conventional AI coding loop can be simplified as **User intent → Code generation → Tests → Feedback → Revision**. A verified workflow introduces another layer: **User intent → Formal specification → Code + proof artifacts → Formal verifier → Feedback → Revision**. If verification fails, the model can revise either the implementation itself or the proof structure used to verify it.

The important shift is therefore not simply from weaker coding to better coding. It is a shift in **where trust is placed**. Tests tell us whether a program worked on the examples we executed, while formal verification asks whether a precisely stated property follows under the rules of a formal system.

> The goal is not necessarily to make the model perfectly trustworthy, but to make its outputs independently verifiable.

This pattern is not entirely new. **AlphaGeometry** combined a neural model that proposed useful constructions with a symbolic deduction engine that derived consequences according to explicit rules. <citation key="trinh2024alphageometry"></citation> Recent work on theorem proving and vericoding extends a similar idea toward much larger mathematical and software artifacts.

Anthropic's recent formalization of **Fermat's Last Theorem (FLT)** is a particularly interesting example. Claude did not discover a new proof of FLT. It followed a simplified exposition of Andrew Wiles's proof and translated the required mathematical dependencies into **Lean**, producing tens of thousands of intermediate formal theorems over roughly eleven days. The achievement is therefore less about solving FLT again and more about transforming a large body of human mathematics into a form that can be **mechanically checked**.

## 2. Formalization and Theorem Proving

A **formal system** defines the language, objects, and inference rules under which a statement can be proved. **Formal methods** is the broader field that uses such systems to specify and verify mathematics, software, hardware, and protocols.

Within this framework, **formalization** means translating an informal mathematical concept or argument into a precise formal object. **Theorem proving** means constructing a proof for that object, while **formal verification** mechanically checks whether the resulting proof or program really satisfies the formal statement.

<figure>
    <img src="https://d2acbkrrljl37x.cloudfront.net/MatrixFigures/Research/2026-anthropic-fermat-dag.webp" />
</figure>
For example, we can define the relation **“is a multiple of”** as follows.

```lean
def MultipleOf (d n : ℕ) : Prop :=
  ∃ k, n = d * k

theorem multiple_of_30_is_multiple_of_10
    (n : ℕ)
    (h : MultipleOf 30 n) :
    MultipleOf 10 n := by

  rcases h with ⟨k, hk⟩
  refine ⟨3 * k, ?_⟩
  rw [hk]
  ring
```

This theorem proves that **if an arbitrary natural number `n` is a multiple of 30, then it must also be a multiple of 10**.

- **`h : MultipleOf 30 n`** means that there exists some `k` such that `n = 30 * k`.
- **`rcases`** extracts that `k` together with the equality `n = 30 * k`.
- **`refine ⟨3 * k, ?_⟩`** proposes `3 * k` as a new **witness**, so that `n` can be written in the form `10 * (...)`.
- **`rw [hk]`** substitutes `30 * k` for `n`.
- **`ring`** verifies the remaining algebraic equality `30 * k = 10 * (3 * k)`.

In ordinary mathematics, this reasoning is simply **“if n = 30k, then n = 10(3k), so n is a multiple of 10.”** Lean expresses this short argument as a formal proof.

> Of course, this is ultimately a **formal proof language**, so it is not necessary to understand every piece of syntax. The important point is that a human or an LLM writes a proof script, Lean turns it into a formal proof, and the **kernel checks whether that proof actually satisfies the theorem statement**.


A few operations capture much of this basic process:

| Operation | Role | Example |
| --- | --- | --- |
| **Unification** | Matches variables and types between a theorem and the current goal | Match a theorem variable $x$ with the current variable $n$ |
| **Rewrite** | Substitutes expressions using an established equality | From $n=2k$, replace $n^2$ with $(2k)^2$ |
| **Witness** | Provides or extracts a value for an existential statement | To prove $\exists m,\;n^2=2m$, choose $m=2k^2$ |
| **Apply** | Reuses an existing theorem and turns its assumptions into new goals | From $A\rightarrow B$, reduce a goal $B$ to proving $A$ |
| **Ring normalization** | Converts polynomial expressions into a canonical form | Verify $(2k)^2=4k^2$ |

These operations are not normally chosen by blindly trying every possible tactic. The **shape of the current proof state** strongly suggests the next operation. An existential goal suggests finding a witness, an available equality suggests rewriting, and a polynomial identity suggests algebraic normalization.

This is where LLMs become useful. They can inspect the current goal, retrieve relevant theorems, propose intermediate lemmas, and choose a promising transformation. Lean then determines whether that proposal is formally valid.

## 3. From Mathlib to Fermat's Last Theorem

Formalizing a theorem as large as FLT raises an obvious question. If every proposition requires smaller propositions, and those propositions require still smaller ones, where does the process stop?

The answer is that it eventually reaches mathematics that has already been formalized. For Lean, a large part of this foundation is provided by **Mathlib**, a community-developed library of verified definitions and theorems.

The overall structure can be viewed as:

**Lean foundations → Mathlib → New intermediate theorems → FLT-specific mathematics → FLT**

<figure>
    <img src="https://d2acbkrrljl37x.cloudfront.net/MatrixFigures/Research/2026-anthropic-fermat-flow.webp" />
</figure>


The proof can therefore develop in two directions. From the final theorem, there is **backward decomposition**: what propositions would be sufficient to prove the current goal? From the foundation, there is **forward accumulation**: once a proposition has a verified proof, it becomes a reusable theorem for later steps.

If the final proposition requires $P_1$, $P_2$, and $P_3$, and $P_1$ itself requires $P_{11}$ and $P_{12}$, a dependency graph begins to form. Once the lower-level propositions are verified, they can support the propositions above them.

This is where **Prove2Me** became important in Anthropic's FLT project. <citation key="chen2026prove2me"></citation> Early Claude agents could make local progress, but as the project grew they began to lose track of which results had already been proved, which theorems depended on others, and what other agents were working on.

Prove2Me externalizes this information as a **directed acyclic graph (DAG)** of theorem statements and dependencies. Different agents can work on separate sub-theorems, verified results become reusable nodes, and completed dependencies can propagate upward until the final theorem is closed.

The important architectural point is that the complete proof does not have to exist as one enormous reasoning trace inside an LLM. Instead, it can exist as an external structure of **small, independently verified mathematical states**.

$$
\text{LLM local reasoning}
+
\text{external proof state}
+
\text{formal verifier}
$$

This makes large-scale formalization resemble a form of verified state construction. Claude performs local proof search, Prove2Me maintains the global dependency structure, and Lean determines which results are allowed to become part of the verified state.

## 4. Formal Tools and Verified AI

Lean is one system in a broader ecosystem of **formal methods**. **Lean** is an interactive theorem prover based on dependent type theory: propositions are represented as types, proofs as inhabitants of those types, and the kernel checks the resulting proof terms. **Rocq**, formerly Coq, follows a closely related proof-assistant tradition based on the Calculus of Inductive Constructions. **Isabelle/HOL** uses higher-order logic and combines interactive theorem proving with substantial proof automation.

**Dafny** is oriented more directly toward verified programming. Instead of primarily asking whether a mathematical proposition can be proved, it allows a programmer to attach preconditions, postconditions, and invariants to code and checks whether the implementation satisfies them, largely through verification conditions and SMT solving.

| System | Main focus | Simple example |
| --- | --- | --- |
| **Lean** | Interactive theorem proving | Prove that an even number has an even square |
| **Rocq** | Interactive theorem proving | Prove $\forall n,\;n+0=n$ using tactics or proof terms |
| **Isabelle/HOL** | Higher-order logic and proof automation | State and prove algebraic or logical properties in HOL |
| **Dafny** | Verified programming | Verify that a function always satisfies a stated postcondition |

In this sense, Lean, Rocq, and Isabelle are naturally associated with the question **"Can this proposition be proved?"**, while Dafny is closer to **"Does this program satisfy this specification?"** Vericoding connects naturally to the latter, while AI-assisted mathematical formalization connects more directly to the former.

Formal verification, however, does not automatically solve every problem of trust. Suppose we define $FakePrime(n)$ to mean `True`. We could then formally prove that every number is a `FakePrime`, and Lean would correctly accept the proof. The proof is valid relative to the definition, but the definition does not correspond to what mathematicians mean by a prime number.

This separates **proof correctness** from **semantic correctness**. A formal verifier can check whether a proof satisfies the formal statement, but it cannot by itself guarantee that the formal statement captures what we actually intended. Definitions, specifications, trusted libraries, and allowed axioms therefore remain part of the trust boundary.

This limitation also clarifies what **Verified AI** could mean. It is not simply an LLM with a verifier attached to it. The broader idea is to move part of the burden of trust away from the internal reasoning of the model and toward **artifacts whose correctness can be independently checked**.

> **AI proposes. Formal systems check. Verified results become reusable knowledge.**

Formalization, theorem proving, and vericoding apply this principle to different objects, but they share the same direction: instead of only asking whether an AI appears to reason correctly, ask whether the result it produces can be expressed in a form that another system can verify.
